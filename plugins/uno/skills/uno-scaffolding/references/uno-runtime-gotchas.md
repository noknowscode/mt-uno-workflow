
# Uno Platform Runtime Gotchas & Spec-Time Facts

Load this file **before writing XAML or C# for a specific platform head or control**, before a spec picks a
library or rendering path, and whenever a build, runtime, layout, binding or rendering defect appears or an
app is being verified (build/run/App MCP/UI automation).
Corrections from the 2026-09-25 audit (measured on Uno.Sdk 6.7.30
and 6.6.42, mostly on a Linux X11 desktop host) are tagged `*(audit <ID>)*`; disproved claims are listed at the end.

Adding an entry: follow the workaround protocol in `uno-scaffolding.md`, record repro, versions and what was
measured versus inferred, and export the transcript excerpt via the `handoff` skill.

## Spec-Time Facts (docs / SDK-targets / decompile verified 2026-09-21, MorningCard spec, Uno.Sdk 6.7.30 = Uno.WinUI 6.7.135, Toolkit 9.1.3, Themes 7.1.1, Extensions 7.3.6)

Evidence grade is lower than the Runtime Gotchas below: these were read from docs, SDK targets and assemblies, not measured in a running app. Promote a bullet to the runtime list once a build confirms it.
- **`SkiaRenderer` alone brings `SKCanvasElement`.** `Uno.WinUI.Graphics2DSK` is implicit when UnoFeatures contains `Skia` OR `SkiaRenderer`, or on any desktop TFM (`Uno.Implicit.Packages.ProjectSystem.targets` ~line 101); supported on `netX.0-android` with `SkiaRenderer` (`controls/SKCanvasElement.md`). `Toolkit` + `Skia` also pulls `Uno.Toolkit.Skia.WinUI` (ShadowContainer) implicitly at the SDK's version, so an explicit PackageReference is only needed when `Skia` is absent (the DYT case). The authoritative UnoFeatures list is `uno.sdk/<ver>/Sdk/Sdk.props.buildschema.json`; the docs MCP strips that table.
- **Composition path trimming works on Skia**: `CompositionGeometry.TrimStart/TrimEnd/TrimOffset` map to `SKPathEffect.CreateTrim`, and `Shape.StrokeDashArray/StrokeDashOffset` are implemented. Point-at-length has no XAML/Composition equivalent, so a design that needs positions along a path still needs `SKPathMeasure`. Do not justify a Skia canvas with "XAML cannot draw partial paths".
- **`UISettings.AnimationsEnabled` is hardcoded `true` on Skia desktop** and real on Android. A desktop reduced-motion requirement needs an in-app setting.
- **Android Skia TalkBack is marked WIP** in `features/accessibility/index.md` (Win32, macOS, WASM supported; Linux planned). Do not claim screen-reader support on Android Skia heads without a device pass; record a failure as a gap. Measured on Android (FieldCheck, 2026-09-25): only the first realised `ListViewItem` reaches the uiautomator/TalkBack tree, and disabled buttons are omitted; see Android below.
- **A `KeySpline` control point must stay within 0..1**, so overshoot curves like `cubic-bezier(.34,1.4,.64,1)` cannot be a KeySpline. XAML equivalent: `BackEase EasingMode="EaseOut" Amplitude="0.3"` (5.1% overshoot near 63%); inside a Skia timeline, evaluate the bezier in C#.
- **`utu:Responsive` default breakpoints are 150/300/600/800/1080** (`Wide` fires at 800); a different threshold needs a `ResponsiveLayout` resource. House rule (`uno-scaffolding.md`, *Breakpoints*): every breakpoint is a `{utu:Responsive}` value on an element, structure included (`Grid.Row/Column/ColumnSpan`); not on `ColumnDefinition`/`RowDefinition`, and cached pages use `AdaptiveTrigger` until the Toolkit reconnect fix ships. `ResponsiveView` swaps templates, which recreates its content (entrances replay, state is lost).
- **Material 7.1.1 `ProgressBar` exposes only `ProgressBarBackground/Foreground/Height/MinWidth`** as lightweight keys (no corner radius). Round toggle buttons base on `IconToggleButtonStyle` (`IconToggleButtonBackgroundChecked`, `IconToggleButtonForegroundChecked` + state variants; `ut:ControlExtensions.AlternateContent` for the checked/unchecked icon swap). Material has no segmented style (Cupertino only); `ChipGroup SelectionMode="Single"` needs a named style such as `FilterChipGroupStyle`.
- **`Path.Stroke` does not inherit `Foreground`**: bind it to the templated parent's Foreground inside button styles so stroked icons follow checked/disabled states. `SvgImageSource`/Resizetizer output cannot be recoloured.
- **Focus visuals are per-element properties, not resources**: `UseSystemFocusVisuals`, `FocusVisualPrimaryBrush/Thickness`, `FocusVisualSecondaryThickness`, `FocusVisualMargin`. The ring follows `CornerRadius`; Material also paints its own focused overlay, so neutralise one.
- **Without `FontOverrideSource` (`MaterialLight/Regular/MediumFontFamily`) Material controls stay Roboto** even when app text styles use a custom face. The documented Skia route for weights is a `.ttf.manifest` font manifest; per-weight `FontFamily` resources (see the variable-font bullet below) remain the validated fallback.
- **Material runtime recolour:** `SemanticThemeHelper.PrimarySeed` patches brushes in place but derives HCT tones (not the design's exact HSL) and is frozen by any `OverrideSource` entry for Primary. For exact parity mutate app-level `SolidColorBrush.Color` and point control lightweight keys at those brushes. `ColorOverrideSource` is deprecated in Themes v7 in favour of `<MaterialToolkitTheme.Colors><ut:ThemeColors OverrideSource=".."/>`.
- **MVUX:** `Feed.Combine` fast-starts to None when any parent is None; a null from a service is the documented None signal; `[EnumeratorCancellation]` is required on `IAsyncEnumerable` watch iterators; a generated command stays executing (button disabled) for the whole method, so timed UI resets belong outside the command; a second model needs its own view/ViewMap (or DI-created ViewModel), because a model exposed as a property hands XAML raw `IState`s.
- **`ILocalizationService.SetCurrentCultureAsync` applies on next app start** (docs: "requires an app restart"); live switching is the separate `guides/hotswap-app-language.md` path. `Strings/` folder names must equal the `LocalizationConfiguration.Cultures` entries, and `UseConfiguration(...EmbeddedSource<App>())` must precede `UseLocalization()`. `IThemeService` persists its choice and can only apply after `NavigateAsync` (no window root before that).
- **Android:** edge-to-edge is default on .NET 9+/SDK 35+, so put `utu:SafeArea.Insets` on the scrolling content to keep backdrops full-bleed; `utu:StatusBar.Foreground` is an enum (`Light|Dark|Auto|AutoInverse`); SDK default min API is 21 (projects here use 24); on Android 16+ `BackRequested.Handled` is ignored and any live subscription consumes back (measured in FieldCheck, 2026-09-25; see Android below).
- **Check `dotnet new` template version against the pinned Uno.Sdk**: with `Uno.Templates` 7.0.0-dev installed, a scaffold may emit a 7.0-dev `global.json`. Full non-interactive command that dry-ran clean: `dotnet new unoapp -o <Name> -preset recommended -platforms android desktop -presentation mvux -theme material -theme-service -renderer skia -tfm net10.0 -http none -dsp false -tests none`. FieldCheck (2026-09-25) hit the same trap with `Uno.Templates 7.0.0-dev.6` installed and scaffolded from an isolated hive holding stable `Uno.Templates 6.7.30`.

## Runtime Gotchas

Measured in running apps between 2026-06 and 2026-09 (Uno.Sdk 6.5.36 to 6.8.0-dev, Toolkit 8.4.2 to 9.1.3, Uno.Extensions 7.2.3 to 7.3.6). Each bullet names the project, date and versions it was validated on; re-check on newer releases before relying on it. Bullets marked **Fallback** apply only after the semantic route has demonstrably failed. Entries with an *Evidence audit* line were traced back through their session transcripts on 2026-09-25; the class and confidence there override any stronger wording in the bullet.

### Windowing, startup & desktop host

- **Win32 desktop host: `MainWindow.UseStudio()` blocks window display when no DevServer is reachable - on STABLE too** (validated BillCal, 2026-08-26, Uno.Sdk **6.6.42**, `net10.0-desktop`, Windows). *(audit G01)* Host-dependent, re-verify: the audit did not reproduce it on Linux X11, where a Debug build on 6.6.42 **and** 6.7.30 logs `DevServer isn't able to connect` and the window still shows (with the Hot Design toolbar); Windows 6.7.30 was not tested. Keep the `APP_NO_HOTDESIGN` gate below as a cheap safeguard; the template emits `UseStudio()` under `#if DEBUG`. The process starts and stays alive, but `MainWindowHandle` is `0` and enumerating the process's top-level windows finds **no XAML window at all** (only `GDI+ Hook Window Class`, `IME`, `PseudoConsoleWindow`) - so it is not merely "hidden", it is never created. Console shows `Uno.UI.HotDesign.Client.Logic.DevServer.RemoteControlService: DevServer isn't able to connect` and then nothing. The cause is `UseStudio()`, and it reproduces on stable. Fix: launch via `uno_app_start`, or gate the call - `if (Environment.GetEnvironmentVariable("APP_NO_HOTDESIGN") != "1") MainWindow.UseStudio();` - so headless verification runs can opt out. Note a desktop Uno app is a windowed process: redirected stdout/stderr capture **nothing**, so add a file-based trace if you need startup diagnostics.
  - **`UseStudio()` also carries the App MCP connection on desktop** (MorningCard, 2026-09-23): gating it off for a forced TV/watch layout left `uno_app_start` reporting "RemoteControl client did not connect" and every screenshot timing out. Gate it only for headless runs or Android form factors; keep it on for desktop App MCP work.
  - For captures of the GL-composited window use `PrintWindow` with `PW_RENDERFULLCONTENT` (see the automation bullets for its blank-bitmap trap); gdigrab region capture records whatever covers those pixels, and window-title gdigrab returns black.
- **Creating a secondary `Window` disturbs the main window's FullScreen presenter on `net10.0-desktop`** (validated DeskBoardUno, 2026-07-31, Uno.Sdk 6.6.42, Win32 host). *(audit G08)* Win32-only until re-verified: the audit did not test presenter behaviour on another host or on 6.7.30. `[field note 6.6.42 / Win32]`. Details: applying `OverlappedPresenter.SetBorderAndTitleBar`/`AppWindow.Resize` to a secondary window *before* its first activation can hit the main window instead (main reverts to overlapped-maximized, rect −8,−8); even a clean secondary-window close can knock the main FullScreen presenter out. Fix: defer the secondary window's presenter/size/position work to its first `Activated` with a non-deactivated state, and after the secondary window closes re-assert the main overlay (~300 ms delay, then cycle `SetPresenter(Default)` → `SetPresenter(FullScreen)` - a plain re-`SetPresenter(FullScreen)` can no-op because AppWindow thinks it's already fullscreen). Also: subscribe deactivate-to-close handlers only after first activation, or the popup closes itself during the activation race.
- **`AppWindow.MoveAndResize` is a silent no-op on `net10.0-desktop`** (validated DeskBoardUno, 2026-07-31, Uno.Sdk 6.6.42): the call returns without effect and the window keeps its default rect - the Uno0001 analyzer warning is truthful. *(audit G10)* It is `[NotImplemented("__SKIA__")]` in Uno Platform's `AppWindow.cs` and had no runtime effect on X11 either `[verified: 6.7.30 / X11]`. The DeskBoardUnoPoc "MoveAndResize ok" log line was a false positive (no exception ≠ resized). Replace it with `AppWindow.Move` + `AppWindow.Resize` (both implemented in source; the audit could not observe them under a window-manager-less Xvfb). For fullscreen overlays use `AppWindow.SetPresenter(AppWindowPresenterKind.FullScreen)`. Ex-style stripping, `WS_EX_TOOLWINDOW`, topmost via `SetWindowPos`, and `ShowWindow(SW_HIDE/SW_SHOW)` cycles all work on the host HWND, and the Skia swapchain survives repeated hide/show (three cycles verified by composited screenshots).
- **`AppWindow.Resize` grows the frame before the Skia surface follows** (validated LightWidget, 2026-08-04, `net10.0-desktop`, Win32 host). *(audit G54)* Win32 field note: an intermittent race the audit could not test (Xvfb without a window manager cannot resize); keep the advice, re-verify on 6.7.30. Details: the app lays out to the new size against the old surface and renders **clipped**, with bare window behind the missing strip. Intermittent - it depends on whether the resize lands before the first render, so it reproduces maybe one run in three. Re-asserting on `Activated` + `SizeChanged` does not reliably fix it (guarding on `AppWindow.Size` short-circuits because the *frame* is already the target size while the surface is not). If a fixed window size is not a hard requirement, don't resize at all and let the layout fit whatever the window is. If a harness needs a known render size, pin the content instead (set explicit `Width`/`Height` on the root `Viewbox`) rather than sizing the window.
- **A large window resize on Uno Skia desktop leaves stale pixels where the layout changed shape** (validated MorningCard, 2026-09-22, Uno.Sdk 6.7.30, `net10.0-desktop`). Collapsing the default 1024x640 window (a wide two-column stage) straight to 520x1120 (the narrow single-column stage) left text from the old layout painted under the new one: every chip label in a `ChipGroup` appeared to carry a ghost copy drifting further right across the row, plus a stray "68" that turned out to be the cabin-temperature value from the wide layout's slider row. **It is in the app's own surface, not the capture**: `PrintWindow` and a direct `CopyFromScreen` show it identically, and a visual-tree dump reports exactly one `TextBlock` per chip, untrimmed, unoverlapped, nothing extra. Any **second** relayout repaints the band and it is gone, which is why it looked intermittent. Consequence for verification harnesses: **size the window twice** (target+8, settle ~900 ms, then target) before capturing, or a first-frame capture will show artifacts that do not exist in the running app and send you hunting a control bug. Generalises past chips - suspect it for any ghost text after a harness resize.
  - *Evidence audit (2026-09-25):* test-environment artifact; medium confidence. Seen only after a programmatic `SetWindowPos` resize; the 1024 to 520 trigger is inferred, and one artifact appeared with no resize at all.
- **FileOpenPicker** works on Skia desktop and must be called on the UI thread; MVUX commands may run off it, so marshal via the window `DispatcherQueue` (`TryEnqueue`) and bridge back with a `TaskCompletionSource`. On WinUI/WinAppSDK only, the picker also needs `InitializeWithWindow`.
- **The WinAppSDK and Desktop heads share the same `%LOCALAPPDATA%\<App>` folder** on one machine (FieldCheck run 2), so data saved on one head appears on the other. Reset both between test runs.

- **`IThemeService.SetThemeAsync` called while navigation is still constructing the model never completes; no exception, no log** (measured Lapse, 2026-09-29, Uno.Sdk 6.7.30, Extensions 7.3.6, `net10.0-desktop`). A trace showed "apply index=2 service=ScopedThemeService current=System" and never the line after the `await`. The same call from a state initializer delayed ~1.5 s (after the page loaded) returned `changed=True now=Dark` at once. Related: `IState.ForEach` does not fire for the state's initial value, so a theme state wired only through `ForEach` never applies a start value, and resolving `IThemeService` from `Host.Services` in `OnLaunched` changed nothing (it is not the window-scoped instance). Pattern that works: user picks call the model's injected `IThemeService` (post-load); a pinned start theme is applied after load. Repro: `State.Value(this, () => { _ = Theme.SetThemeAsync(AppTheme.Dark); return 2; })` in a model created by `InitializeNavigationAsync`. Lapse `MainModel.InitialTheme`, marked `WORKAROUND(IThemeService before window root)`.

### Rendering, Composition & Skia

- **Composition blur: the audit found `CompositionEffectBrush` rendering on Skia; a Win32 measurement found it painting nothing. Host-dependent, re-verify on your head before relying on either.** *(audit G03)* Audit result `[verified: 6.6.42 (Uno 6.6.184) + 6.7.30 (Uno 6.7.135) / desktop / X11]`: a hand-written GaussianBlur effect brush renders blurred output both over a colour source and over `CompositionVisualSurface` (the exact chain below). The Skia compositor code is shared across hosts, but Win32 was not re-tested. Practical rule now: verify on your host with the colour-brush sprite control first, use blur where it renders, and keep an opacity/translate/scale fallback for entrances. The original Win32 measurement follows as history.
  - *Win32 measurement (BillCal, 2026-08-26, Uno.Sdk 6.6.42, `net10.0-desktop`):* `CompositionEffectBrush` painted nothing while reporting `LoadStatus.Success`. The note then read: this is the real reason Composition blur is unavailable - *not* "the Win2D wrapper is internal", which is only half true. Isolated step by step: `Compositor.CreateSpriteVisual()` + `ElementCompositionPreview.SetElementChildVisual` **renders** (a colour brush filled the window pure `255,0,0`); `CompositionVisualSurface` with `SourceVisual`/`SourceSize` **captures correctly** (a plain `CreateSurfaceBrush(surface)` painted a visible copy of the subtree); but swapping that same surface brush behind a `CompositionEffectBrush` renders **nothing at all**. The effect is genuinely recognised - internal `EffectHelpers.GetEffectType(CLSID_D2D1GaussianBlur)` returns `GaussianBlurEffect`, which is in its supported enum alongside ~30 others. Not a property-mapping bug either: baking the amount in before `CreateEffectFactory` and answering both `BlurAmount`/`StandardDeviation` in `GetNamedPropertyMapping` (returning `Unknown` rather than throwing for unrecognised probes) changed nothing. **What IS public and usable:** `Compositor.CreateVisualSurface/CreateSurfaceBrush/CreateEffectFactory/CreateSpriteVisual`, `CompositionVisualSurface`, `CompositionEffectBrush`, `SpriteVisual`, and `IGraphicsEffect` / `IGraphicsEffectD2D1Interop` / `GraphicsEffectPropertyMapping` (in `Uno.dll`, namespace `Windows.Graphics.Effects[.Interop]`) - only `Microsoft.Graphics.Canvas.Effects.GaussianBlurEffect` is internal, and hand-writing that description is ~40 lines and compiles fine. So the blocker is the render step, not the API surface. **Docs pointer (added 2026-09-21, MorningCard spec, NOT yet runtime-tested):** `features/shapes-and-brushes.md#acrylicbrush-rendering-on-skia` documents a Skia-native `AcrylicBrush` path that bypasses the effect brush entirely: `<AcrylicBrush AlwaysUseFallback="False" media:AcrylicBrushExtensions.UseCompositionEffectBrush="False" TintColor=".." TintOpacity=".."/>` (`xmlns:media="using:Microsoft.UI.Xaml.Media"`), with the constraint that the element has **no children on Android** (use a childless Border behind the content). For frosted-glass *surfaces*, try that first on the current Uno.Sdk, then `SaveLayer` backdrop in an `SKCanvasElement`; the Win32 measurement applies to hand-built `CompositionEffectBrush` graphs and blur-in *entrances* on that host. Its original consequence ("treat Composition blur as unavailable on Skia desktop") is superseded by the audit result above: keep entrances readable on opacity + translate + scale alone, and keep the capability probe (`TryAttach` returning null) so blur lights up where the effect brush renders. Re-verify with a colour-brush sprite first - if that does not paint, the problem is your host element, not the effect.
  - *Win32 measurement (Cargo, 2026-10-01, Uno.Sdk 6.7.30, `net10.0-desktop`, Windows 11):* the Skia-native `AcrylicBrush` path (`AlwaysUseFallback="False"`, `media:AcrylicBrushExtensions.UseCompositionEffectBrush="False"`, childless `Border`) **renders a real backdrop blur** on Win32 (not the fallback colour). Its radius is fixed and large: 13-15 px text under it measured luminance 233-250 on a white panel (effectively erased) at TintOpacity 0.1 and 0.45 alike. For "blur back" of readable content, stop the layer at Opacity ~0.75 so the text reads through as soft focus. Evidence: Cargo `Presentation/ActivityView.xaml` (blur-back layer).
- **A Storyboard replaced mid-run can leave its animated values in force on Uno 6.7 Skia desktop** (Cargo, 2026-10-01, Uno.Sdk 6.7.30, Win32, not reduced to a minimal page). Pattern: `Stop()` a running board on an element, set the new local values, `Begin()` a new board on the same properties (FillBehavior Stop, G60 style). Intermittently (about 1 in 3 rapid open/close pairs, and once on a slow switch-then-close) the element stayed at the old animated values while the model, binding and callbacks were all correct (traced). Moving final-state work from `Completed` to a timer did not help, which points at `Stop()` itself. What held: step the values yourself as local values (elapsed-time tween) and write the end state on the last step; no Storyboard. Evidence: Cargo `Controls/Reveal.cs`.
- **`CompositionTarget.Rendering` is not a steady frame clock on Skia desktop: it fires only while frames render** (Cargo, 2026-10-01, Uno.Sdk 6.7.30, Win32). A tween stepped from it stalled short of its end once the last sub-pixel steps dirtied nothing (a 14 px gap was left where a panel should have collapsed), and on a quiet page steps arrived 80-260 ms apart. Step from Rendering for frame sync, but guard the end state with a one-shot `DispatcherQueueTimer` at duration + ~40 ms. Related measurement: the Cargo Overview idle frame interval was median 17.8 ms, p90 45.6, p99 206, max 767 (irregular hitches, not tied to its 1 s clock), so any short animation can land on a hitch; profile the page before blaming the animation. Evidence: Cargo `Controls/Reveal.cs`, `Controls/Harbour/HarbourView.xaml.cs` (OnStageHeightChanged).
- **Liquid Glass / backdrop effects on Skia targets (validated LiquidGlassLab, 2026-06, Uno.Sdk 6.5.36 / SkiaSharp 3.119.2):** `SKCanvasElement.RenderOverride` draws on the same canvas the window renders to, so `canvas.SaveLayer(in SKCanvasSaveLayerRec { Backdrop = filter })` genuinely samples live app content behind the element. SkiaSharp 3.119 has **no** `SkImageFilters::RuntimeShader` binding, and neither does any release through 4.152.1 / 4.154.0-preview.1 *(audit G34; SaveLayer backdrop itself not runtime-tested by the audit, `[field note LiquidGlassLab 6.5.36]`)* - route SkSL through `SKImageFilter.CreateShader(builder.Build())` as the *displacement input* of `CreateDisplacementMapEffect` for refraction. Chromatic aberration = 3 displacement filters at split scales + channel-isolating color matrices + `CreateArithmetic` recombine.
- **`SKRuntimeShaderBuilder` must be created once and cached.** *(audit G35)* Mechanism (decompiled, 3.119.2 and 4.152.1): `SKRuntimeEffectBuilder.Dispose()` disposes its `Effect`, so a per-frame `using` on a builder frees the `SKRuntimeEffect` it shares; never `using` a builder built on a cached effect, and set uniforms per frame on the cached builder. When it goes wrong, the next render AVs with `0xC0000005` in `sk_runtimeeffect_get_uniform_byte_size`. Symptom: first frame fine, crash on next invalidation (e.g. drag). Also: never build Skia filter DAGs per frame in `RenderOverride` (render thread) - cache against built-with values and snapshot DPs to plain fields on the UI thread.
- **`UIElement.Opacity` does not affect `SKCanvasElement` drawing, and neither does an ancestor's `Opacity`** - the canvas draws straight onto the window canvas, bypassing the XAML opacity. Bake the alpha into the Skia paint/colors (validated LagoonSpecimen, 2026-07). *(audit G38)* Own Opacity 0.3 and parent Opacity 0.3 both left pure (255,0,0) while a XAML Border faded to (255,179,179). `[verified: 6.6.42 + 6.7.30 / X11, SkiaSharp 3 and 4]`
- **Uno's `Path.Data` elliptical arcs: fixed on Skia in Uno 6.7, still throw on 6.6.x and on native renderers (`-renderer native`).** *(audit G47)* On 6.6.x, `A rx,ry` with rx≠ry throws `NotImplementedException` ("arc must be based on a circle") during parse, which is a startup crash if the Path is in initial XAML (validated DesignSkillEval run 11, 2026-08-03, Meridian Release exe died before first frame; audit reproduced it with compiled XAML and `XamlReader`). Uno 6.7 Skia uses `SKPath.ArcTo` with separate radii and renders them. `[verified: throws 6.6.42, renders 6.7.30]` On 6.6.x or a native renderer, compose curves from circular arcs (`A6,6`) or Béziers instead.
- **`SKCanvasElement` DOES ride a parent `ScaleTransform` / `Viewbox`** (validated LightWidget, 2026-08-04, Uno.Sdk 6.6.42, `net10.0-desktop`). A `Viewbox Stretch="Uniform"` wrapping a fixed-size Grid that contains both an `SKCanvasElement` and XAML `TextBlock`s scales both together and keeps them pixel-registered - the canvas is not drawn at unscaled window resolution. This closes the open question in the shared-element morph bullet. It makes "design at literal spec coordinates, scale the whole surface uniformly" the correct pattern for fixed-aspect Skia surfaces: put every measured value in the markup/renderer at its real number and let the Viewbox handle sizing. Note the renderer still receives the *unscaled* design size in `RenderOverride`'s `area`, so blur sigmas and stroke widths stay in design units (no manual DPI math). *(audit G52)* A 4 px stroke rendered ~12 px in a 3x Viewbox with `area` = 100x100. `[verified: 6.7.30 / X11]`
- **Shared-element morph on Skia desktop: translate-only is a taste call, not a platform limit.** *(audit G58)* The original premise (that an `SKCanvasElement` might not ride a scale) is closed by the Viewbox bullet above: it scales correctly. LagoonSpecimen v2: sizing the showcase card equal to its docked board slot let the explode be a pure `TranslateTransform` on the overlay, and translate moves the canvas cleanly. Keeping scale off the app card and putting the choreography in the staggered tile entrances remains a design preference.
- **An oversized `CornerRadius` (the WinUI "999 pill" idiom) renders as an oval on the Skia renderer** (validated Measures, 2026-08-27, Uno.Sdk 6.6.42, desktop + Android): the radius is reduced per axis instead of clamped to a circle, so an 81x28 button gets 40x14 elliptical corners. Write half the height (`CornerRadius="14"` for 28 epx). *(audit G59)* `[verified: 6.6.42 + 6.7.30 / X11]`
- **A finished `HoldEnd` storyboard keeps overriding the local value; a replay that sets `Opacity = 0` and then animates it up after a `BeginTime` shows the held 1 through the whole delay** (Measures, 2026-08-27). *(audit G60)* Standard WinUI precedence (WinUI semantics, not an Uno Platform quirk): after completion Opacity reads 1 after setting 0, and `Stop()` releases it. `[verified: 6.7.30 / X11]` Stop the previous board on the same (target, property) before starting a new one - Measures `Motion/Anim.cs` keeps a `ConditionalWeakTable<DependencyObject, Dictionary<string, Storyboard>>` for exactly this.
- **`LinearGradientBrush` `SpreadMethod="Repeat"` with `MappingMode="Absolute"` works on Uno Skia, desktop and Android** (MorningCard v6, 2026-09-23, Uno.Sdk 6.7.30), so a CSS `repeating-linear-gradient` hatch can be a brush. Hard stops are not antialiased, though: a 1 px 135° line at 6 px pitch steps thick/thin along its length (visible at 1x desktop, still visible at 2.6x on Android). For even line weight, draw the lines in an `SKCanvasElement` (1 px AA stroke, clipped to the round rect). At ~10% ink the difference is negligible.
  - *Evidence audit (2026-09-25):* not a defect (capability check); high confidence. Planned spike; line-weight judged by eye, not pixel sampling.
- **`BrushTransition` on Uno Skia interpolates `SolidColorBrush.Color` only and drops the brush's `Opacity`, so an Opacity-based brush renders as solid colour** (measured Cargo, 2026-09-30, Uno.Sdk 6.7.30, `net10.0-desktop`, Windows). Rows whose `Border.Background` swapped between `SolidColorBrush(Ink){Opacity=0}` and `{Opacity=.06}` under `<BrushTransition Duration="0:0:0.15"/>` all painted solid ink; the same brushes without the transition rendered correctly, and no Uno0001 warning fires. Fix: put the alpha in the colour (`Color.FromArgb(a, r, g, b)`, brush Opacity 1) for any brush a transition animates (Cargo `Tokens.Tint`). Not reduced to a minimal repro. Evidence: Cargo/docs/evidence/2026-09-30-brushtransition-drops-opacity.md
- **A dash `PathEffect` on `SKCanvas.DrawLine` painted nothing; the same paint on `DrawPath` works** (MorningCard v6, 2026-09-23, SkiaSharp 3.119.2 bundled, `net10.0-desktop`). Draw dotted lines as a two-point `SKPath`.
  - *Evidence audit (2026-09-25):* framework bug, unisolated; low confidence. One desktop A/B with a near-zero on-interval (`[0.1, 8]`) and a round cap. Not reduced and not tried on Android; scope the claim to that case.

- **A `Path` whose geometry has zero height (a lone horizontal line, `M6 12h12`) draws nothing on Uno Skia desktop; the same stroke with any vertical extent renders** (measured Destination Rolodex, 2026-10-07, Uno.Sdk 6.7.30, `net10.0-desktop`, Windows 11). ### Performance & frame pacing

- **A held `CompositionTarget.Rendering` subscription forces the Uno Skia desktop compositor to produce frames at display refresh FOREVER, at ~50-70% of one core** (probe-validated TransitionsGallery, 2026-08-17, Uno.Sdk 6.6.42, `net10.0-desktop`; cost is mostly per-frame composition/present - likely a vsync busy-wait in the swap - and is identical in Release). Per-frame cost measured ~11-15ms of CPU per frame *regardless of content*; an app that "idles" with a Rendering hook attached is a 60fps app. Consequences: (a) use Rendering only for one-shot animations that unsubscribe on completion; (b) drive continuous decorative loops (shimmers, pulses) from a shared ~30fps `DispatcherTimer` that calls `Invalidate()` - a timer does not force frames, each invalidation produces exactly one, and co-subscribed loops coalesce into the same frame; (c) a `RepeatBehavior="Forever"` storyboard has the same permanent-pump cost and cannot be throttled - port slow decorative storyboard loops to the timer. **A Forever storyboard keeps costing while its target is hidden; `Stop()` does reclaim it** (isolated repro `ComponentStatesLab/PulseCpuRepro`, 2026-08-18, Uno.Sdk 6.8.0-dev.12, `net10.0-desktop`, **Release**, 3 samples/mode after a 15s settle): app idle **0.1%** of one core, Forever opacity keyframe animation on one 220×24 `Border` running **29.4%**, same storyboard running with the target `Visibility="Collapsed"` **17.3%**, after `Stop()` **0.3%**. Two consequences: (a) one trivial decorative animation costs ~a third of a core, so budget them; (b) **collapsing a skeleton layer does not stop its animation** - always `Stop()` on state exit, or use a `DispatcherTimer` writing `Opacity` (0-2%) which cannot be orphaned. Also probe-confirmed: invalidation is per-element (a dirty `SKCanvasElement` does NOT re-execute other elements' `RenderOverride`), so caching settled Skia content into `SKPicture` buys nothing on this target.
  - *Audit (2026-09-25), host-dependent timer cost:* *(audit G23)* The pump and `Stop()` findings reproduced on Linux X11/Xvfb (software GL), 6.7.30, % of one core: idle 0.1-2.3, Rendering 56 (60 callbacks/s), Forever storyboard 63-65, collapsed target 52-57, after `Stop()` 0.1-0.3. **But a 30 fps `DispatcherTimer` writing `Opacity` cost 56-57 %, not 0-2 %** (6.6.42: same pattern at ~21 %). The 0-2 % timer figure above is a Windows GPU measurement; on software GL the timer costs as much as the pump. Budget decorative loops per host and measure on the target machine. `[verified: 6.6.42 + 6.7.30 / X11]`
  - *6.7 vs 6.6 on software GL:* the same probe on the same host cost ~56 % of one core for continuous frames on 6.7.30 vs ~21 % on 6.6.42; idle was similar. Observation only (Xvfb/llvmpipe, no GPU), not a verified regression; re-measure on a Windows GPU before acting. *(audit NEW-05)*
- **`Timeline.AutoReverse` is Uno0001 (not implemented) on Skia.** The analyzer flags `Storyboard.AutoReverse`; build ping-pong loops from explicit keyframes instead. *(audit NEW-03)* `[verified: 6.7.30 / build]`
- **`EffectiveViewportChanged` behaves as in WinUI; never read its Uno0001 members.** *(audit G24, NEW-01)* The event's `EffectiveViewport` is in the element's own coordinates: an element 2,050 px down a 200 px ScrollViewer receives `0,-2050,300,200`, which correctly does not intersect its bounds. - **`Opacity` on a container that covers the screen (a grain/texture layer) becomes a full-screen offscreen surface re-composited every frame; on a Pixel 8 that was a worst frame of 91 ms during a swipe** (Measures, 2026-08-27). ### Binding, MVVM & MVUX

- **MVUX bindable generation is recursive over feed value types and fails on modern record shapes** (validated BillCal, 2026-08-26, Uno.Extensions.Reactive 7.2.3). With implicit bindables on - or with `[ReactiveBindable(true)]` on the model - the generator emits proxies for *every* type its feeds carry, then fails to compile them: `CS9035` for records with `required` members, and `CS0019`/`CS0023` (`??` and `?.` on a non-nullable) for `record struct` types. Also `KE0001`: any record with an `Id`/`Key` property must be `partial`. Options: make the domain records `partial` and non-`required`, or - when nothing binds two-way through XAML - set `[assembly: ImplicitBindables(IsEnabled = false)]` and bind `FeedView.Source` to the plain model record as the `DataContext`; `IFeed<T>` resolves through `{Binding}` directly. Note the attribute takes a named argument (`IsEnabled = false`), not a positional bool: the positional parameter is a namespace pattern string, so `ImplicitBindables(false)` fails with CS1503. *(audit G05)* `[verified: 6.7.30 / build]`
- **Nullable value-type state: write the type argument.** *(audit G06)* The untyped inference form `State.Value(this, () => (int?)null)` infers `IState<int>` and fails with `CS0266`. `State<int?>.Value(this, () => null)`, `State<int?>.Empty(this)` and `UpdateAsync(_ => null)` all compile, so `IState<int?>` is fine. `[verified: 6.7.30 / build]` (The earlier "`IState<T>` will not accept a nullable value type; use a sentinel" note generalised the inference failure; see the Disproved section.)
- **MVUX generator reserves `Model`** on the generated ViewModel - a feed/state named `Model` on the model record collides (CS0102). Pick another name (e.g. `Graph`). *(audit G13)* `[verified: 6.7.30 / build]`
- **Nullable reference-type state is a style choice.** *(audit G14)* `IState<string?> => State<string?>.Empty(this)` compiles with no errors or nullability warnings. The house preference is still `IState<T>` non-nullable + `State<T>.Empty(this)`: absence is None, FeedView's `NoneTemplate` renders it, and you clear with `UpdateAsync(_ => null)` (also compiles). `[verified: 6.7.30 / build]`
- **Inside a FeedView ValueTemplate, reach the page VM via `{Binding Parent.X}`** (FeedViewState exposes Parent). *(audit G16)* ValueTemplate only: it is the only template whose DataContext is `FeedViewState` (ErrorTemplate gets the thrown exception, ProgressTemplate a bool). Scope, host-dependent, re-verify: the audit resolved a **state-like** `Parent.Title` in a ValueTemplate `[verified: 6.6.42 + 6.7.30 / X11]`, while MorningCard (2026-09-22, 7.3.6, Windows desktop) saw state properties fail to resolve through `Parent` (see the `Parent.X` state entry under Binding); commands held in both. ElementName-to-page bindings work inside ItemsRepeater item templates (`{Binding DataContext.X, ElementName=Root}`), so per-item DPs can observe page state.
- **`{Binding Refresh}` inside `FeedView.ErrorTemplate` is a silently dead button** (validated ComponentStatesLab, 2026-08-17, Uno.Sdk 6.8.0-dev.12). *(audit G28)* `[verified: 6.6.42 + 6.7.30 / X11]`: `{Binding Refresh, ElementName=...}` re-runs the feed and recovers. The ErrorTemplate's DataContext is the **thrown `Exception`**, not `FeedViewState` - confirmed by `uno_app_get_element_datacontext`, which serialised the Retry button's DataContext as `System.InvalidOperationException` with the service's own message and zero `Refresh`/`FeedViewState` members. `Command` binds to null, the button still renders enabled and still reports `[i]` invoke, and clicking it does nothing. `{Binding Parent.X}` fails there for the same reason (Parent lives on FeedViewState). Fix: `x:Name` the FeedView and use `Command="{Binding Refresh, ElementName=TheFeed}"`, which resolves even from inside a nested `CardContentControl.ContentTemplate`. This one is dangerous because it is invisible to review, to the build, and to screenshots - the error state *looks* perfect. Verify Retry by driving the app to Error, flipping the data source healthy at runtime, invoking the button, and asserting the service ran again.
- **`Feed.AsyncEnumerable(source)`** is the MVUX way to project an `IAsyncEnumerable<T>` push stream (e.g. a service that yields the current value then live updates) into an `IFeed<T>`; the VM projection updates live (`{Binding Live}`). **To read the latest value in a command, name a method parameter after the feed** (`CaptureLive(int live)` for feed `Live`); MVUX injects the current value. **Do not `await` an AsyncEnumerable feed inside the model:** it restarts the cold enumerable and returns its first value (1 while the VM showed 18-22), even when the feed is cached in a `{ get; }` initializer. *(audit G30)* `[verified: 6.7.30 / X11]`
- **FeedView needs a record (or list) feed; over a primitive feed it never leaves the Progress template.** *(audit NEW-02)* The generated VM projects `IFeed<int>` / `IFeed<string>` as a plain `int` / `string` property, so `<FeedView Source="{Binding Count}">` receives `System.Int32` and stays in ProgressTemplate forever, even for a trivial `Feed.Async`. Record feeds (projected as `Bindable*ViewModel`) work. Bind primitive feeds directly (`<TextBlock Text="{Binding Count}"/>`), or wrap the value in a record when you need FeedView states. `[verified: 6.6.42 + 6.7.30 / X11, generator v2 and v3]`
- **`{Binding Parent.X}` inside a `FeedView` template resolves commands but NOT state** (validated MorningCard, 2026-09-22, Uno.Extensions.Reactive 7.3.6). `Parent.SomeCommand` works; `Parent.SomeState` silently fails to resolve, and every binding on it falls back to its property default - `Visibility` to **Visible**, a bound `Angle` to **0**. An `IState<T>` always has a value, so it joins a `Feed.Combine` without the None propagation that a feed parent would cause. ### App MCP, Hot Design & UI automation

- **App MCP (uno-app devserver) flow:** the MCP server is `dotnet dnx -y uno.devserver -- --mcp-app` started in the project dir (`-y` answers the first-run `dnx` install prompt for non-interactive starts; DevServer 6.7.135 initialises in 2.8-6.3 s, discovers the `.sln` and reports Healthy) *(audit G17)*; `--mcp-wait-tools-list` holds the `tools/list` reply until the **devserver upstream** connects (~3.7 s on a warm `dnx` cache, no app launch needed), then returns the full set at once. It must start when a `.sln` exists (reconnect via `/mcp` after scaffolding); launch the app with `uno_app_start`, not bare `dotnet run`.
- **Project `.mcp.json` is loaded from the session root, not the shell's working directory** (validated AotLaunchLab, 2026-08-04). A session started in a parent folder never registers the project's `uno-app` server at all. `cd` into the project does not retroactively load it, and `/mcp` only reconnects already-registered servers - it will happily report "Reconnected to uno" (the global HTTP docs server) while `uno-app` stays absent, which reads as a successful reconnect. Check for `uno_health` / `uno_execute_tool`: if the only Uno tools are `uno_platform_docs_search` / `_fetch`, the app MCP was never loaded and no reconnect will fix it. Start a fresh session rooted in the project folder.
  - The `.sln` must exist at session start (Chefs reskin, 2026-08-27): scaffolding inside a session leaves `uno-app` unregistered until a fresh session is started in the project folder. Headless fallback that worked: `dotnet <App>.dll` (not the exe) with `APP_NO_HOTDESIGN=1`, a DEBUG start-route hook that resolves seed data through the services, and `PrintWindow` captures.
- **Whether the app tools are listed directly depends on `--mcp-wait-tools-list`** (re-validated 2026-08-12, DevServer 6.6.184, raw MCP stdio client; supersedes the RefractionPixels 6.6.166 note that said the tools are always proxied). Measured on 6.6.184:
  - **With** the flag: `tools/list` is held ~3.7 s and returns **all 16 tools directly** - the 14 real `uno_app_*` / `uno_health` / `uno_devserver_diagnostics` tools *plus* the `uno_discover_tools` / `uno_execute_tool` bridge pair. Call the real tools by name.
  - **Without** the flag: `tools/list` replies in ~200 ms with **only the four bridge tools** - `uno_health`, `uno_app_select_solution`, `uno_discover_tools`, `uno_execute_tool`. The rest arrive later via a `notifications/tools/list_changed`, so a client that ignores that notification is stuck at four. Invoke the real ones as `uno_execute_tool {toolName: "uno_app_start", arguments: {...}}`; names and schemas are unchanged, only the call path moved.

  - Diagnostic: seeing only four tools means the flag is missing (or the client dropped the notification), not that the App MCP is broken. `uno_discover_tools` confirms the upstream set either way.
- **`uno-app` emits `tools/list_changed` without declaring `tools.listChanged`** (validated 2026-08-12, DevServer 6.6.184; still true on 6.7.135 *(audit G20)*).
